**Вывод: подключить Auth без доработок нельзя.** Его настоящий access token проходит
собственный parser, но получает HTTP 401 в текущем middleware Chat. Первичная проверка
выполнена с реальными JWT-компонентами обоих репозиториев и заглушками Project/User;
затем результат подтверждён через работающие Auth:8080 и Chat:18080 с реальными БД
(подробности повторной проверки ниже).
Сервисы можно интегрировать без переписывания Chat и без изменения числовых ID в Auth.

## Блокирующие различия

| Контракт | Auth сейчас | Chat сейчас | Что требуется |
| --- | --- | --- | --- |
| Подпись JWT | HS256, общий `JWT_SECRET` | Только RS256, публичный RSA PEM | Auth подписывает приватным RSA-ключом; Chat получает только публичный |
| Claims | `uid`, `sub`, `iat`, `nbf`, `exp` | Дополнительно обязательны `iss`, `aud`, `project_id`, `roles`, `token_use=access` | Согласовать и выдавать полный контракт при login и refresh |
| Project | Нет контекста Project в login/session/JWT | Один разрешённый Project на токен, проверка trusted issuer/audience в БД | Хранить разрешения пользователя на Project и проверять их на стороне Auth |
| Роли | Глобальные `user`, `moderator`, `admin`, читаются из Auth DB | В JWT допустимы только `user`/`admin`, действуют в указанном Project | Разделить глобальные роли Auth и права в конкретном Chat Project |
| Отзыв доступа | Статус пользователя проверяется в БД на каждом защищённом Auth-запросе | JWT проверяется локально; статусы/сессии Auth не запрашиваются | Определить задержку применения блокировки, понижения роли и logout |

### P1 — алгоритм и обязательные claims

Auth `token/jwt.go:25–40` выпускает HS256 без контекста приложения и Project.
Chat `internal/auth/auth.go:86–126` сначала требует корректный `project_id`, затем
проверяет подпись, issuer, audience, срок действия, назначение и роли. Поэтому добавление
одного claim или замена одного ключа несовместимость не устраняет.

Auth parser (`token/jwt.go:48–55`) также принимает только HS256. При смене алгоритма
необходимо согласованно изменить и выпуск, и проверку JWT внутри Auth, сохранив `uid`
для его middleware либо переведя middleware на проверенный `sub`. Нельзя ослаблять
проверки Chat или передавать ему приватный ключ ради совместимости.

### P1 — Project и роли не имеют общего источника прав

Auth `auth/model.go:5–10`, `auth/dto.go:12` и `auth/service.go:546–557` описывают
глобальные роли и login без Project. В Chat `admin` предоставляет административные
права внутри Project; `moderator` зарезервирован требованиями для membership группы/канала,
а не для глобального JWT. Текущий verifier отклоняет JWT с ролью `moderator`.

Просто скопировать глобальную роль Auth в JWT недостаточно. Нельзя автоматически делать
глобального Auth admin администратором всех Chat Projects. Нужны серверные grants
пользователь → Project → роли. Полученный от клиента Project ID должен проверяться
по этим grants; refresh не должен позволять сменить Project или сохранить отозванные права.

### P1 при требовании немедленного отзыва — lifecycle аккаунта и сессии

Auth middleware (`internal/transport/http/auth_middleware.go:40–48`) отклоняет запросы
неактивного пользователя. Изменение статуса блокирует refresh-сессии
(`auth/service.go:571–586`); logout отзывает refresh token (`auth/service.go:299–304`).
Изменённые глобальные роли Auth читаются из БД при последующих защищённых запросах.

После согласования JWT Chat продолжит принимать ранее выпущенный access token до `exp`
с текущим допуском 30 секунд, если нет независимого локального ограничения Chat.
Ни события отзыва, ни introspection, ни проверка версии сессии сейчас не подключены.
Logout в самом Auth также не отзывает уже выпущенный access token: его middleware
проверяет состояние аккаунта, но не refresh-сессии. Сброс пароля имеет аналогичное
ограничение относительно access token.

Нужно явно выбрать допустимую задержку: короткий TTL либо дополнительная проверка/доставка
отзыва с определённым поведением при недоступности Auth. Локальный ban Chat с режимом
read-only не эквивалентен глобальной блокировке Auth, запрещающей доступ целиком.

## Что совместимо и что учитывать при запуске

- **Идентификаторы совместимы:** Auth уже записывает числовой ID строкой в `sub`.
  Chat хранит эту строку как `external_user_id` и создаёт свой UUID; идентичность задаётся
  парой `(project_id, external_user_id)`. Переход Auth на UUID не нужен.
- **Refresh остаётся в Auth:** его непрозрачный случайный refresh token не требуется
  превращать в JWT или передавать в Chat. Меняется контракт выдаваемого access token.
- **Разные Go-библиотеки не препятствуют интеграции:** репозитории остаются отдельными
  сервисами со своими зависимостями и миграциями; общий Go module не требуется.
- **Профили отдельные:** `/api/v1/users/me` Auth и `/api/v1/me` Chat имеют разные схемы.
  Автоматической синхронизации профиля сейчас нет; это не блокирует JWT-аутентификацию.
- **HTTP-порты:** Auth `.env.example:1` и стандартный Chat Compose используют 8080.
  При запуске на одном хосте назначить разные опубликованные порты либо отдельный ingress.
  Фактические пользовательские `.env` и секреты в ходе проверки не читались.
- **Базы данных:** сохранить отдельные БД и миграции. При стандартном search path оба
  migrator используют `public.goose_db_version`, но независимые номера миграций; Chat
  отклоняет неизвестные версии при проверке схемы. Таблицы Chat находятся в schema `chat`,
  однако это не изолирует общую таблицу истории миграций. Направлять оба текущих migrator
  в одну БД без доработок нельзя. Разные БД на одном PostgreSQL-сервере допустимы.
- **Переменные окружения различаются:** Auth ожидает `dev`/`prod`, Chat —
  `development`/`test`/`production`. Не использовать общий `APP_ENV` без преобразования.
- **CORS в Auth Compose:** `internal/config/config.go:41` читает `CORS_ALLOWED_ORIGINS`,
  но `docker-compose.yml` не передаёт её в `auth` и `auth-debug`. Значение из `.env.example`
  само по себе не поступает в environment контейнера. Для браузерного клиента с отдельным
  origin нужно передать allowlist явно. Это не блокирует серверную JWT-проверку.
- **Swagger:** Auth имеет `/swagger/`, Chat — `/docs/api`. При изменении login/refresh,
  claims и ошибок обновить соответствующие спецификации; в этом review endpoints не менялись.

## Дополнительный риск в refresh, обнаруженный при чтении кода

Auth `auth/repository.go:309–316` обновляет сессию только по ID и выставляет
`revoked_at = NULL`. Проверка её активности сделана раньше отдельным чтением
(`auth/service.go:249–274`). Если отзыв сессии произошёл между чтением и обновлением,
refresh может снова сделать её активной; два параллельных refresh также могут пройти
проверку одного старого токена. Это вывод по SQL/последовательности вызовов,
не результат воспроизведения гонки на PostgreSQL. При последующей HTTP-проверке восемь
одновременных refresh дали одного победителя и семь отказов; опасное чередование
операций в этом запуске не возникло. Это не устраняет разрыв между SELECT и UPDATE.

До интеграции следует сделать ротацию атомарной: проверять прежний token hash,
активность и срок сессии в том же UPDATE, не сбрасывать отзыв, а отсутствие обновлённой
строки считать отказом. Семантику конкурентного отзыва всех сессий/блокировки пользователя
проверить отдельно с реальной БД.

## Предлагаемый порядок интеграции — ещё не реализован

1. Зафиксировать модель Project grants и границы глобальных ролей Auth; определить
   допустимую задержку блокировки, logout и изменения прав.
2. Доработать Auth: Project/session binding, RSA signing/parser, полный контракт claims
   в login и refresh, атомарную ротацию. При refresh читать актуальные grants.
3. Создать доверенный Project в Chat через существующий operator CLI: одинаковые
   Project UUID, HTTPS issuer и audience на обеих сторонах. Подключить публичный ключ
   Auth через `AUTH_PUBLIC_KEY_FILE`; приватный ключ хранить только в Auth.
   Текущий Chat поддерживает один публичный ключ для одного Auth trust domain;
   JWKS и автоматическая ротация потребуют отдельной реализации.
4. Если одного TTL недостаточно, реализовать выбранный механизм отзыва в обоих сервисах.
   Права membership, локальные bans и feature flags по-прежнему проверяет Chat.
5. Развести порты/БД/environment, настроить CORS и маршрутизацию, обновить Swagger и
   содержательные комментарии к новой логике в соответствии с правилами проекта.
6. Проверить реальный login → Chat profile → refresh → Chat; отказ для неверных
   issuer/audience/Project/алгоритма, изоляцию двух Projects, смену прав, блокировку,
   logout и конкурентную ротацию. Только после этого считать интеграцию завершённой.

## Первичная проверка до запуска сервисов

- Auth: `go test -race -count=1 ./...`, `go vet ./...`, `go build ./...` — успешно.
- Chat: `go test -race -count=1 ./internal/auth ./internal/identity/... ./internal/policy/... ./internal/platform/admission ./api/openapi` — успешно.
- Локальный harness `build/auth-compat/compatibility_test.go` импортирует оба репозитория
  через local module replacements. `go test -race -count=1 -v ./...` из его каталога
  прошёл: 10 сценариев. Настоящий токен Auth отклонён Chat с 401 без создания пользователя;
  HS256 даже с полными claims, пропущенные обязательные claims и `moderator` отклонены;
  синтетические RS256 `user`/`admin` с полным контрактом приняты, `sub="42"` сохранён.
- Harness и его зависимости находятся в игнорируемом `/build/`, используют временные
  ключи в памяти, не обращаются к БД и не печатают credentials. Это локальный инструмент
  review, не переносимый integration suite и не реализация нового контракта в Auth.
- Полный сценарий с запущенными Auth/Chat/PostgreSQL не выполнялся. Доставка email/SMS,
  production deployment, миграции Auth на реальной БД и `auth-vue` не проверялись.
- Исходники и конфигурация сервисов не изменены; добавлен только этот отчёт и запись
  в локальном `Agents.md`. Commit/push не выполнялись; Phase 2 не начата.
