# Оценка незавершённых изменений Chat после исправления Auth

> Исторический отчёт. По следующему запросу Auth опубликован (`21a8b3a`), Chat переведён на прямую проверку Auth и локальные роли. Актуальный контракт: [Identity](IDENTITY.md), решение D32. Описанные ниже draft-ограничения относятся к моменту проверки.

Дата: 2026-08-30. Scope текущего запроса: исправить найденные проблемы сессий Auth,
реализовать отзыв access JWT, затем проверить необходимость ранее сделанных изменений Chat.
Код и миграции Chat в ходе этой оценки не изменялись, не удалялись и не развёртывались.

## Что изменилось в Auth

Auth сохраняет HS256 и HTTP-форматы login/refresh/logout. JWT теперь содержит `sid` и
уникальный `jti`; защищённый запрос проверяет состояние сессии в БД. Logout отзывает
access JWT до и после refresh, включая конкурентную ротацию. История refresh digests
позволяет logout найти ту же сессию по старому токену. Блокировка и смена пароля
отзывают сессии атомарно. Права Chat/Project в Auth JWT не добавлялись.

Локальная проверка одной подписи JWT по-прежнему не сообщает об отзыве. Для немедленного
logout Chat должен проверять предъявленный access token через Auth без положительного
кеша; общий секрет подписания передавать Chat не требуется.

## Что в Chat сейчас не завершено

- `go build ./...` проходит, но `go test -race -count=1 ./...` падает на трёх сценариях
  `TestAccessContract`: `admin`, `moderator`, `no-roles`. Tests всё ещё считают JWT
  источником ролей, в отличие от изменённого verifier. Это известное незавершённое
  изменение, а не подтверждение готовности Chat.
- Seed и документация всё ещё описывают admin из JWT. Для локальных ролей нужно
  операторское назначение ролей и обновление dev fixtures; нельзя назначать admin
  первому вошедшему или копировать глобальную роль Auth.
- Swagger Chat не описывает draft session endpoints. Проще убрать лишние endpoints,
  затем описать прямой bearer Auth и ошибки недоступности Auth.
- Старые `auth_issuer`/`auth_audience` остаются в Project schema для прежнего RSA пути;
  remote path их не использует. Их наличие не требует немедленного удаления данных.
- В режиме remote текущий draft создаёт отдельные Chat-сессии. Развёрнутый Chat API
  не обновлялся этой задачей; полный live login/logout через Chat API не объявляется готовым.

## Проверки, выполненные в этом запросе

Auth: full `go test -race -count=1 ./...`, `go vet ./...`, `go build ./...`;
OpenAPI validation и совпадение опубликованной спецификации с файлом репозитория.

PostgreSQL: новый `TestSessionTransactions` создаёт отдельную случайную schema,
применяет старые/новую миграции и проверяет backfill, одного победителя refresh,
гонки logout/refresh, expiry, blocking/reactivation и password reset со stale login.
Fixture schema удалена после проверки.

HTTP Auth: регистрация, два независимых login, refresh, logout со старым refresh,
повторный logout, 401 для обоих access JWT и актуального refresh после logout,
сохранение другой сессии, восемь конкурентных refresh, гонка logout/refresh и повторный login.
Тестовый аккаунт, сессии, история digests и связанные fixture-данные удалены.

Дополнительно **существующий `auth.Remote` из Chat** проверен против настоящего Auth:
до logout принимает JWT и возвращает ID без прав admin; после logout возвращает
`ErrUnauthenticated`. Здесь Project resolver был заглушкой; это проверка механизма
интеграции, не полного развёрнутого Chat API.

## Рекомендуемый следующий шаг — не выполнен в этом review

Удалить только добавленный draft слоя Chat-сессий и миграцию 5, подключить remote verifier
напрямую, завершить локальные роли/операторское назначение/seed, обновить Swagger и tests.
Затем проверить login → Chat → refresh → Chat → logout → Chat 401 на реальных сервисах.
Общий Auth при этом не требует дальнейшего изменения формата JWT или добавления прав Chat.

Commit/push не выполнялись. Никаких новых изменений реализации Chat после запроса
о проверке необходимости не сделано; этот отчёт фиксирует результат оценки.
